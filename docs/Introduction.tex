\section{Introduction}
\label{introduction}

\IEEEPARstart{L}{earning-based} circuit models are increasingly used to approximate expensive analyses in electronic design automation (EDA), supporting tasks such as resource estimation, timing prediction, and congestion analysis~\cite{lopera2021survey}. By learning relationships between circuit structure and design properties, these models can provide fast feedback for optimization across different stages of the design flow. Graph neural networks (GNNs) are a natural choice for many such tasks because they can represent operations, cells, and their dependencies as graphs. Their effectiveness, however, depends on how the circuit-modeling problem is formulated, not simply on the capacity of the neural backbone. Developing an accurate predictor requires choices about the circuit information supplied to the model, the computation used to process it, and the objectives used to guide training.

These choices are closely coupled to the target EDA task. For timing prediction, for example, circuit connectivity determines how delay-related information propagates, while cell characteristics and path dependencies affect the quantities to be predicted~\cite{guo2022timing}. A generic aggregation scheme may fail to distinguish dependencies that play different roles in the timing calculation. Improving such a model can therefore require a change to the representation or propagation mechanism rather than an increase in network depth. In practice, human model developers address these issues through an iterative process: they examine prediction errors and training behavior, identify limitations in the current formulation, implement a revised modeling strategy, and evaluate whether it resolves the observed problem. Repeating this process across AI-for-EDA (AI4EDA) tasks demands both domain expertise and substantial implementation and experimentation effort.

Conventional GNN neural architecture search (GNN-NAS) automates part of this process by exploring a predefined design space~\cite{gao2019graphnas,zhou2022auto}. Experts specify the available operators, aggregation functions, layer configurations, and other searchable choices before exploration begins. A search algorithm then selects configurations according to a prescribed performance objective; reinforcement-learning-based approaches, for example, use validation performance to construct a reward. This formulation is useful for selecting effective combinations of available components, but the resulting models remain bounded by the choices encoded in the search space. A new circuit relation, a task-specific propagation rule, or a revised supervision strategy cannot be discovered if the corresponding modification is not expressible in that space. Moreover, a performance score indicates which candidate is better under the chosen objective without necessarily explaining why the current circuit model fails or what modeling change could address that failure.

Large language models (LLMs) offer an opportunity to automate more of the model-development process. Recent research agents demonstrate workflows that connect idea generation, code implementation, and experimentation~\cite{lu2024aiscientist}. For circuit modeling, the central opportunity is to use an LLM to interpret the current model and its experimental behavior in the context of the EDA task, then translate that analysis into an executable improvement. For example, errors concentrated on long timing paths may motivate a revision to information propagation, whereas large relative errors for small target values may motivate a different training objective. Such observations suggest candidate explanations and changes to test; their value must still be established experimentally. The available modeling strategies can thus expand during exploration as the agent develops new implementations, while a fixed validation protocol remains the basis for judging progress.

We present \textbf{CircuitModelPilot}, an agentic framework for automated circuit modeling across AI4EDA tasks. Given a task specification and an initial model, CircuitModelPilot coordinates a repeated cycle of \emph{performance analysis, modeling revision, code generation, training, and validation}. The LLM examines the current model, validation errors, training behavior, and prior experiment records to identify potential modeling limitations. It then proposes a concrete change, implements the corresponding code, and uses the resulting evidence to decide what to explore next. The framework supports changes across circuit representations and features, neural architectures and propagation mechanisms, and learning objectives. These dimensions organize the modeling decisions without requiring every candidate implementation to be listed in advance. Training hyperparameters can be tuned within a separate inner search, allowing parameter optimization to complement changes to the model formulation.

Making this cycle effective requires organizing alternatives across many experiments. A single sequence of edits can become committed to an unproductive direction, while independent trials can repeatedly rediscover the same limitations. CircuitModelPilot therefore organizes exploration as a \textit{model-design search tree}. Each node stores a candidate model together with its implementation, training configuration, validation results, and analysis; each edge records a modeling change relative to its parent. The agent selects a parent using both its observed performance and the accumulated analysis, develops a new candidate, and adds the resulting experiment to the tree. This structure supports branching from promising models, comparing alternative refinements, revisiting earlier candidates, and pruning directions that repeatedly fail to improve performance. Both successful and unsuccessful experiments inform subsequent decisions, helping allocate the search budget to useful directions.

Reliable comparisons are equally important: an apparent gain should reflect a modeling improvement rather than a changed data split or evaluation procedure. CircuitModelPilot gives each candidate a separate implementation workspace, checks the proposed changes before execution, and records the code and configuration used in each experiment. Within a task, candidates follow a consistent validation protocol, and the held-out test set is reserved for final reporting. These controls make it possible to reproduce a candidate, compare it with its parent, and revisit an earlier branch. A common task interface supplies the circuit representation, prediction target, training and evaluation entry points, and allowed implementation scope, enabling the same agent workflow to operate across tasks with different modeling requirements.

We evaluate CircuitModelPilot on HLS resource prediction, netlist-level timing prediction, and RTL-to-netlist timing prediction. The evaluation compares its generated models with human-designed predictors, fixed-space automated search, and LLM exploration without structured experiment management. It examines predictive performance, the modeling changes discovered during search, and the contribution of experiment review and tree-based memory to reliable iterative improvement. The objective is to reduce manual circuit-modeling effort while pursuing task-specific predictors that match or exceed human-designed baselines.

The main contributions are as follows:
\begin{itemize}
\item \textbf{An agentic circuit-modeling framework.} We introduce CircuitModelPilot to automate the cycle from analyzing model performance and proposing modeling improvements to generating code, training candidates, and evaluating the results across AI4EDA tasks.
\item \textbf{Tree-structured, adaptive model exploration.} We organize candidate models and experiment records in a search tree that supports branching, refinement, and reuse of prior findings. LLM-generated changes span representation, computation, and learning objectives, extending exploration beyond a predefined catalog of model configurations.
\item \textbf{Reproducible experimentation and cross-task evaluation.} We combine isolated candidate implementations, pre-execution checks, and consistent evaluation protocols, and assess the framework across three EDA prediction tasks against human-designed and automated baselines.
\end{itemize}
