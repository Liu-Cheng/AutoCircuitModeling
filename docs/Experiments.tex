\section{Experiments}
\label{exp}

We evaluate \sysname as an AutoResearch framework for EDA graph prediction. The evaluation addresses two complementary questions: whether the designs discovered by \sysname improve predictive performance, and whether its trace-grounded protocol produces attributable and efficient research decisions. We first describe a common experimental setup, then report overall predictive results, analyze representative discoveries, and examine the contributions of the protocol and discovered mechanisms.

\subsection{Experimental Setup}
\label{sec:exp_setup}

\subsubsection{Tasks and Datasets}
\label{sec:tasks_datasets}

We evaluate \sysname on EDA graph-prediction tasks spanning multiple design abstractions: HLS resource prediction, netlist-level timing prediction, and RTL-to-netlist timing prediction. HLS resource prediction operates on program- or operation-level graphs and estimates implementation quantities such as critical-path and resource-related targets. Netlist timing prediction operates on logic or timing graphs, where directed connectivity and path dependencies determine delay-related quantities. RTL-to-netlist timing prediction uses RTL-level structural information to estimate downstream timing-related targets. Together, these tasks require distinct graph representations, propagation mechanisms, and learning signals.

For every task, we report the graph construction, prediction target, dataset size, split, and evaluation metric. All compared methods for the same task use the identical data split and task interface.

\subsubsection{Evaluation Protocol}
\label{sec:evaluation_protocol}

Each task is evaluated within one fixed ResearchContext. The context fixes the dataset split, selection metric and direction, loss semantics, seed policy, training budget, and evaluation protocol. A candidate is compared only with traces created under the same context. Thus, child-parent differences are attributable to the declared intervention rather than to a changed split, metric, or training budget.

Each run selects its checkpoint using the task's validation protocol and then evaluates that checkpoint on a fixed test split. The resulting validation-and-test bundle is used for trace comparison, result analysis, and subsequent research decisions. Neither validation nor test metrics are used to train model parameters. Promising candidates are re-evaluated according to the configured confirmation procedure before being treated as supported mechanisms.

\subsubsection{Baselines}
\label{sec:exp_baselines}

We compare \sysname with three baselines representing progressively less constrained forms of model design.

\noindent\textbf{Human-designed baseline.} For each task, we begin with an established task-specific GNN and its corresponding graph construction, trainer, and metric contract. This model initializes the root trace and provides the reference point for candidate-parent comparisons.

\noindent\textbf{Fixed-space automated search.} This baseline searches a predefined space of approved GNN configurations and training parameters. It can optimize candidates already present in this space, but it cannot introduce a new task representation, propagation mechanism, or learning signal.

\noindent\textbf{Naive LLM exploration.} This baseline receives the same task profile, trace-local editable modules, starting model, and training budget as \sysname. It does not use the structured hypothesis card, unified Candidate Review, or trace-guided analysis protocol. It isolates the value of HEDGE's research protocol from the general ability of an LLM to modify code.

All automated methods receive the same task-specific starting point and matched trace or compute budget. They use the same split, metric, loss, epoch budget, and seed policy within each task.

\subsubsection{Implementation Details}
\label{sec:exp_implementation}

Candidates are implemented in trace-local generated modules. Representation interventions are realized through graph-pass modules, computation interventions through model or convolution modules, and learning-signal interventions through trainer modules. Before execution, the runtime validates the declared editable scope, generated-file interfaces, parent lineage, context consistency, and review-artifact freshness. Each completed trace retains its source snapshot, parent-relative diff, configuration record, execution summary, and analysis record.

For a fixed semantic candidate, task-approved parameter search may optimize training parameters within a declared search space. This inner optimization is recorded separately from the semantic intervention, so learning-rate, dropout, batch-size, or related changes cannot be presented as the EDA mechanism itself. We report each task metric in its natural direction and report mean and standard deviation under the prescribed seed policy whenever multi-seed evaluation is used.

\subsection{Overall Predictive Performance}
\label{sec:overall_performance}

We first evaluate whether the designs selected by \sysname improve predictive performance. For every task and target, we compare the final HEDGE-selected design with the human-designed baseline, fixed-space automated search, and naive LLM exploration under the common protocol above. The main comparison reports the task metric, variability across the prescribed seeds, and the relative change from the root baseline.

This experiment evaluates the practical utility of open semantic exploration. It does not assume that one architecture should dominate every EDA task. Instead, results are interpreted at the task level: an improvement is connected to the supported trace or traces that introduced the corresponding mechanism, whereas a non-improvement indicates that the explored directions did not yield a stronger design under the available budget.

\subsection{EDA-Native Mechanism Discovery}
\label{sec:mechanism_discovery}

Overall performance alone does not show whether \sysname discovered a mechanism beyond a fixed search space. We therefore analyze representative trace trajectories. For each selected trajectory, we report the parent observation, the EDA objects and analysis rule named in the hypothesis card, the intended semantic level, the trace-local implementation delta, and the resulting evidence.

The HLS resource-prediction traces provide a representative case. Rather than selecting a different generic backbone, candidate traces can introduce operation- or dependency-specific mechanisms, such as controlled use of resource-related operation attributes, prior reinjection, or propagation along an explicit program dependence. A candidate is considered an EDA-native discovery only when its mechanism is absent from the initial fixed space, its hypothesis and implementation pass the relevant reviews, and its final trace analysis supports the claimed effect. A favorable proxy result that fails confirmation is retained as refuted or inconclusive evidence rather than reported as a discovery.

\subsection{Ablation Study}
\label{sec:ablation}

\subsubsection{Ablation of HEDGE Protocol Components}
\label{sec:protocol_ablation}

We next isolate the contribution of the protocol components that make HEDGE a trace-grounded AutoResearch framework. Starting from the full system, we remove one component at a time: (i) the unified Candidate Review, (ii) the scoped realization constraint, or (iii) structured trace memory and analysis. The ablations use the same task context and trace budget as full HEDGE.

We evaluate these variants with trace-level reliability measures: the rate of grounded proposals, execution success rate, rate of comparable child-parent experiments, detected scope or alignment violations, replay success rate, and the fraction of initially promising candidates that survive confirmation. These results show whether each protocol component improves the quality and interpretability of the exploration process, independently of a final accuracy gain.

\subsubsection{Ablation of Discovered EDA Mechanisms}
\label{sec:mechanism_ablation}

Protocol ablation explains whether HEDGE explores reliably; it does not explain why a discovered GNN design improves prediction. For each representative supported mechanism, we therefore compare the full design with controlled variants that remove or alter its essential component. For example, a resource-prior reinjection mechanism can be compared with the root GNN, input-only injection, layer-wise injection without gating, and a randomized-prior control. The exact variants are determined by the mechanism under study and must preserve the common training protocol.

This analysis distinguishes a genuine EDA mechanism from an improvement caused merely by additional parameters or an uncontrolled auxiliary feature. We report only mechanism ablations whose variants correspond to explicit, implementation-aligned hypotheses.

\subsection{Discussion and Limitations}
\label{sec:exp_discussion}

HEDGE constrains exploration within a task interface and trace-local editable scope; it does not claim to autonomously redesign arbitrary EDA flows or infer missing domain semantics without a task profile. The quality of its hypotheses depends on the domain descriptor, templates, and diagnostics supplied by the task adapter. Similarly, separating the Candidate Reviewer and result analyst from the proposer reduces self-confirmation within the workflow but does not establish statistical independence between LLM outputs.

The framework also does not eliminate ordinary sources of experimental variance. Small data regimes, stochastic training, incomplete parameter search, and task-specific implementation constraints can make a promising trace unstable. We therefore report negative and inconclusive outcomes, apply configured confirmation procedures, and avoid interpreting an isolated gain as a general conclusion. Cross-task generality refers to the common trace-based protocol; the useful semantic mechanisms remain task-dependent.
